# news — локальный аудит Telegram-канала

Скептичный аудит Telegram-канала по фиксированному шаблону (`prompts/channel_audit_prompt.md`),
выполненный **полностью локально, на стандартной библиотеке Python**, без токенов и без API.

Промт фиксирован; меняется только «база» — Markdown-экспорт канала.
Логика промта зашита в код, поэтому каждый запуск детерминирован и воспроизводим.

```
python3 analyze_channel.py data/sample_channel.md --md out/report.md --json out/report.json
```

---

## Зачем

Через LLM такой анализ стоит токены на каждый прогон, а при канале в ~4000 постов
не влезает в контекст целиком. Здесь тот же шаблон исполняется как программа:

| | через LLM | здесь |
|---|---|---|
| 12 постов | ~10–15k токенов | 0.3 с, 0 токенов |
| 3879 постов (8.9 МБ) | не помещается | 18.9 с с дедупликацией (15.3 с без неё), 0 токенов |
| воспроизводимость | нет | побайтово (проверено тестом на разных `PYTHONHASHSEED`) |
| объяснимость оценок | нет | `--explain <id>` |

## Установка

Ничего ставить не нужно. Python ≥ 3.9, только стандартная библиотека:

```bash
git clone <repo> && cd news
python3 -m unittest discover -s tests     # 42 теста
```

## Использование

```bash
python3 analyze_channel.py ЭКСПОРТ.md [ключи]
```

| Ключ | Что делает |
|---|---|
| `--md PATH` | отчёт в фиксированном Markdown-формате промта |
| `--json PATH` | машина-читаемый результат: индексы, категории, темы, практики, красные флаги, аудитории, вердикт и все посты |
| `--explain ID` | разбор одного поста: оценки, все сработавшие сигналы, структура |
| `--handle @name` | username канала, если в экспорте его нет |
| `--own-domains d1,d2` | домены, считающиеся собственными (не подтверждают ссылку на источник) |
| `--quiet` | прогресс в stderr отключён |

Если `--md`/`--json` не указаны, отчёт печатается в stdout.

Коды выхода: `0` — успех, `1` — файл не читается или в нём нет постов,
`2` — не задан путь к экспорту (печатается справка). Ошибки вывода понятным
сообщением в stderr, без traceback.

## Python API

```python
import textforge

result = textforge.analyze_file("data/sample_channel.md", own_domains=["sdelaem.agency"])
print(result.analysis.indices["usefulness"], result.analysis.verdict["label"])

result.markdown            # отчёт в формате промта
result.data["red_flags"]   # dict (даты уже приведены к строкам)
```

`analyze_file` возвращает `AnalysisResult` (отчёт + dict + `ChannelAnalysis`).
CLI делает то же самое через `analyze` и печатает результат через
`render_markdown`/`to_json`; `to_dict` и `to_json` дают одинаковые данные.

## Как промт отображается в код

Каждый пункт шаблона имеет конкретный модуль. Меняя поведение, правьте не отчёт, а источник.

| Раздел промта | Код |
|---|---|
| Разбор экспорта, даты, `**Views:**`, текст поста | `textforge/tgparser.py` |
| Нормализация, токены, RU-стеммер, предложения | `textforge/text.py` |
| Деньги, проценты, ссылки, телефоны, законы, цитаты | `textforge/extract.py` |
| Дубли и самоповторы (MinHash + LSH + Jaccard) — режут оригинальность и попадают в слабые стороны | `textforge/dedup.py` |
| Русские словари сигналов | `textforge/lexicons.py` |
| Быстрый матчер (суффикс корня, префиксы, `*`-термины, дедуп по `(группа, корень)`) | `textforge/scanner.py` |
| Индексы, категории, красные флаги, аудитории, вердикт | `textforge/analyze.py` |
| Формат вывода, `to_dict`/`to_json` | `textforge/report.py` |
| CLI | `textforge/cli.py` |

### Индексы 0–100

Все четыре индекса — взвешенные по числу слов средние постов (короткие посты не тянут канал вниз).

* **Полезность** — плотность практических маркеров ×7 (до 30) + подзаголовки ×4 (12) + нумерованные
  строки ×3 (10) + списки ×0.8 (6) + числа ×0.5 (8) + деньги/проценты ×2 (8) + ссылки ×1.5 (5)
  + `log1p(слов)`×5 (22), минус плотность мотивации ×12 и плотность пустых фраз ×3.
  ×0.65 для рекламных постов, ×0.5 при `words < 40`.
* **Экспертность** — каузальные связки («потому что», «поэтому», «из-за»), признание ошибок
  и ограничений, цифры, конкретика; минус громкие заявления, минус «единственный/лучший/уникальный».
* **Оригинальность** — 45 базовых + свои кейсы/опыт (до 25+18) − производные маркеры (до 35);
  потолок 42 для «новость/обзор» и 50 для «реклама/продажа». Дубликаты, найденные
  `dedup.py`, режут её жёстко: точный повтор → не выше 22.0, почти повтор → не выше 34.0.
* **Доверие** — 55 базовых + доказательства/прозрачность/внешние ссылки − заявления ×5
  − манипуляции ×6 − короткий пост −5. Отражает **качество сигналов**, а не истинность утверждений.

### Категории (≤6)

`кейс/разбор`, `гайд/инструкция`, `инсайт/мнение`, `личный опыт`, `новость/обзор`,
`реклама/продажа`. Каждая — сумма сигналов с весами, но с жёсткими воротами:

* **кейс** требует ситуацию + действие + результат (+ желательно причину) — цифры сами по себе не кейс;
* **реклама** засчитывается только по сильным маркерам (слабые слова вроде «ссылка» или «курс»
  не превращают пост в рекламу);
* пост без текста (только медиа) → `прочее` с 0 словами.

### Красные флаги

12 флагов из промта. Флаг попадает в отчёт, только если сработал в ≥3 постах и в ≥5% ленты.
`постоянные продажи` считается отдельно — от доли постов категории «реклама/продажа».

### Вердикт

🟢 `полезность ≥ 70 и экспертность ≥ 62 и оригинальность ≥ 58 и реклама ≤ 20%` →
🟡 при `полезность ≥ 48` → 🟠 при `≥ 32` → иначе 🔴.
Популярность, подписчики и выручка в эти пороги **не входят**: просмотры влияют только на
сортировку «лучших постов» внутри составного `0.5u + 0.2e + 0.2o + 0.1·engagement`.

### ФАКТ / ЗАЯВЛЕНИЕ АВТОРА / ВЫВОД

Разделение сделано структурно: `_facts_block()` печатает только то, что извлекается из текста
регулярными выражениями (суммы, ссылки, проценты), всё остальное попадает в блок
«что остаётся заявлением автора». Никакое внешнее знание в расчёт не берётся;
недостающие поля печатаются как `нет данных`.

## Настройка

Всё тюнится без правки логики:

* `textforge/lexicons.py` — словари (группы: `PRACTICAL_TERMS`, `CLAIM_TERMS`,
  `MANIPULATION_TERMS`, `MOTIVATION_TERMS`, `EXPERT_TERMS`, `VAGUE_TERMS`, `RED_FLAGS`, …);
* пороги и веса — константы вверху `textforge/analyze.py`
  (`MIN_WORDS_SHORT=40`, `AD_USEFULNESS_FACTOR=0.65`, `BEST_POST_MIN_SCORE=55`,
  `PRACTICE_MIN_USEFULNESS=60`, `VERDICT_GREEN=(70, 62, 58, 0.20)`, `VERDICT_YELLOW=48`,
  `VERDICT_ORANGE=32`).

Добавлять в один словарь и `кейс`, и `кейсы` безопасно — сканер дедуплицирует термины по
`(группа, корень)`, так что одна и та же форма не считается дважды.

## Тесты

```bash
python3 -m unittest discover -s tests -v
```

42 теста покрывают: стеммер и токенизатор, экстракторы (деньги/проценты/ссылки/телефоны),
дедупликацию, разбор экспорта (включая посты без `### Text`), сканер (суффикс корня, фразы
с окном в 2 слова, отсутствие двойного счёта), категории, индексы, красные флаги,
вердикт, `to_dict`/`to_json`, инвариант «популярность не повышает полезность»,
коды выхода CLI и побайтовый детерминизм отчёта между процессами
с разными `PYTHONHASHSEED`.

## Ограничения (честно)

* Это статистика по лексиконам и структуре, а не понимание текста: ирония, сарказм
  и сложные конструкции считываются плохо.
* Пороги откалиброваны на 12 постах реального канала + синтетике. На 3879 постах прогон
  проверялся по производительности и отсутствию предупреждений, но не по смыслу.
* `prompts/channel_audit_prompt.md` — шаблон задачи, которому следует код. Он сохранён
  для сверки и может расходиться с исходной формулировкой в деталях; поведение программы
  определяется кодом.
* Сгенерированные отчёты (`out/`) и служебные дампы (`data/_*.md`) в git не попадают.
